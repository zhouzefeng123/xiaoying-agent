# 单窗口无限会话优化方案（SOTA）与 P0 落地说明

## 1. 目标

- 在不降低代码任务成功率的前提下，实现单窗口长期会话稳定运行。
- 将上下文输入规模控制在可预测区间，避免随会话长度线性膨胀。
- 保证历史指令与关键技术状态可持续召回。

## 2. 当前风险

- 历史消息处理存在“先全量再裁剪”的路径，长会话下构建成本上升。
- Warm Context 历史检索如果跨会话混入，会引入错误上下文。
- 上下文裁剪预算以固定字符阈值为主，对不同模型窗口适配不足。

## 2.1 代码审查结论（按当前实现）

- 历史读取热点仍在 `messages.List(sessionID)` 全量加载路径，随后在 Agent 层做窗口裁剪，说明 P0 仍是“应用层降压”，还未消除 DB 侧线性增长风险。
- Warm Context 已做同会话优先重排，但消息检索底层仍是全局用户消息集合，导致会话外数据仍可能进入候选池，仅由后续排序减轻风险。
- 消息写入已为多角色生成 embedding，但检索 SQL 仍只查 `role='user'`，这会降低对“历史代码片段/历史修复方案（常在 assistant 输出）”的召回率。
- 总结锚点机制可用，但历史裁剪与摘要刷新在多路径并行，后续迭代需要保持单一策略入口，避免路径漂移。
- Token 预算已改为模型窗口驱动，但缺少运行时评测阈值与告警线，无法自动判断“效果退化”。

## 2.2 最新进展（2026-03）

- 历史入口已收敛到 `ListWindow`，并在异常时回退旧 `List`，首轮/刷新/紧急恢复路径统一。
- Warm Context 检索已切换为会话内检索接口，降低跨会话污染概率。
- 消息检索角色已扩展为 `user + assistant`，代码修复类历史召回覆盖面提升。
- 记忆写入新增“相似度去重”与“文本归一化去重”双重防线，减少重复记忆堆积。
- 预意图阶段（broad/general）恢复 L2 记忆加载，修复首轮对话记忆不足问题。

## 3. 目标架构（分层记忆）

- L0 程序性约束：用户长期规则、编码规范、安全边界。
- L1 热上下文：最近多轮原始对话，保证当前任务连贯性。
- L2 任务态记忆：当前任务阶段、关键文件、未完成项、失败原因。
- L3 长期记忆：摘要、向量检索与图关联增强。

## 4. P0 范围

P0 只做高收益低风险改造：

1) 会话内消息检索优先  
2) 历史分页加载与锚点裁剪（应用层窗口化）  
3) 更精确的 Token 预算控制（按模型窗口动态预算）

## 5. P0 设计细节

### 5.1 会话内检索优先

- 对 Warm Context 的历史检索结果进行会话优先重排。
- 同一 `session_id` 的结果优先注入；跨会话结果仅作补足，防止召回污染。

### 5.2 历史窗口化与锚点裁剪

- 引入历史窗口上限（消息条数级），在进入上下文准备前先做应用层裁剪。
- 若存在 `SummaryMessageID`，保留摘要锚点并仅拼接其后的近期消息窗口。
- 在历史刷新路径复用同一裁剪逻辑，避免多处不一致。

### 5.3 动态 Token 预算

- 将历史压缩预算从固定字符阈值改为“模型窗口驱动”。
- 预算公式基于模型上下文窗口与 `char_per_token` 估算，动态映射为字符预算。
- 在上下文准备函数内按动态预算截断，降低不同模型上的过裁剪/欠裁剪问题。
- 运行时检索预算与退化路径的当前实现契约，见 `backend/docs/memory_search_budget_contract.md`。

## 6. 验收标准

- 长会话下上下文大小保持稳定，不出现明显失控增长。
- Warm Context 注入中会话外消息占比显著下降。
- 代码任务的修改、编译、回归能力与基线持平或提升。

## 7. 下一步升级方案（P1）

P1 目标：在不明显增加请求延迟的前提下，进一步提升长会话稳定性与代码任务保真度。

### 7.1 改动一：数据库级历史分页与锚点查询

- 现状问题：当前会话历史仍通过全量读取后再裁剪，长会话下 DB IO 与内存开销偏高。
- 改造方向：将“应用层窗口化”升级为“数据库级窗口化”，把历史裁剪前移到 SQL。
- 计划改动：
  - 在 `internal/db/sql/messages.sql` 增加以下查询：
    - `ListMessagesBySessionBeforeID(session_id, before_created_at, limit)`（倒序分页）
    - `GetMessageCreatedAt(id)`（锚点时间）
    - `ListMessagesBySessionFromCreatedAt(session_id, created_at, limit)`（锚点后窗口）
  - 通过 `sqlc` 生成方法后，在 `internal/message/message.go` 新增统一入口：
    - `ListWindow(ctx, sessionID, summaryMessageID, limit)`。
  - `internal/llm/agent/agent.go` 在初始加载、循环刷新、摘要后刷新、紧急恢复四条路径统一改为 `ListWindow`。
  - 保留降级开关：当分页查询报错时自动回退到旧 `List` 逻辑。
- 预期收益：每轮历史加载复杂度由“随会话长度增长”下降为“近似常量”。

### 7.1.1 实施前置检查

- 确认 `messages` 表已有 `(session_id, created_at)` 复合索引；若没有，先补索引再上线分页。
- 验证 `created_at` 精度与排序稳定性，避免同毫秒消息顺序漂移。
- 预留 `limit` 配置项，区分首轮窗口和循环窗口。

### 7.2 改动二：结构化任务态记忆（Task State）

- 现状问题：当前记忆对“任务进度/文件清单/失败原因”主要依赖自然语言摘要，精确回放能力不足。
- 改造方向：新增轻量结构化任务态块，作为 L2 上下文稳定注入。
- 计划改动：
  - 在 `internal/llm/agent/agent_context.go` 增加 Task State 注入槽位（位于 Warm Context 前）。
  - 在 `internal/llm/agent/agent.go` 每轮工具执行后更新 Task State（仅保留最近版本）。
  - 在 `internal/memory/service.go` 增加按会话和类别读取最近记录能力（建议 `task_state` 类别）。
  - 增加一致性策略：Task State 与最近工具结果冲突时，以工具结果为准并记录冲突计数。
- 推荐字段：
  - `goal`、`current_step`、`pending_items`、`done_items`
  - `active_files`、`recent_errors`、`next_action`
- 预期收益：跨多轮代码修改时，模型能持续保持“当前做到哪一步”的一致认知。

### 7.3 改动三：工具输出结构化压缩

- 现状问题：大输出主要采用 head/tail 截断，关键信号可能丢失。
- 改造方向：按工具类型做结构化提取，再拼接小体积摘要。
- 计划改动：
  - 在 `internal/llm/agent/agent.go` 大输出处理路径中引入“结构化摘要器”。
  - 对 `RunCommand` 输出提取：错误栈、失败命令、退出码、关键日志片段。
  - 对 `Read`/`Grep` 输出提取：文件路径、命中行号区间、上下文片段。
  - 对代码任务增加“保真白名单”：报错堆栈、补丁片段、文件路径与行号不得被二次压缩。
- 预期收益：在压缩 token 的同时保留“可执行修复”所需关键信息。

### 7.4 P1 验收指标

- 500+ 轮会话下，单轮历史加载耗时显著下降。
- 代码任务多步执行中，任务状态丢失率明显降低。
- 大工具输出场景下，定位错误与修复成功率高于 P0 基线。
- Warm Context 命中中会话外消息占比持续低于阈值（建议 < 5%）。
- 同类任务（代码修复）首轮到第三轮的关键文件召回率不低于 P0。

## 8. 下一步升级方案（P2）

P2 目标：建设可持续演进的长期记忆系统，支持“单窗口无限会话”的质量闭环。

### 8.1 分层摘要索引

- 将摘要分为 `turn_summary`、`task_summary`、`session_summary`。
- 采用增量合并策略，避免每次重写全量摘要。
- 注入时按优先级与 token 预算进行分层装配。

### 8.2 记忆重排评分升级

- 在向量相似度基础上叠加时间衰减与访问热度。
- 推荐综合评分：`similarity + recency + access_count`。
- 降低陈旧记忆对当前任务的干扰概率。
- 建议增加硬过滤：会话域、项目域、类别域先过滤，再做打分排序。

### 8.3 GraphRAG 受控扩展

- 先取 Top-K 锚点，再按边权和扩散半径做受控扩展。
- 防止图谱扩展导致上下文膨胀。
- 仅在任务型/编码型请求启用高强度扩展。

### 8.4 自动评测闭环

- 增加长会话基准场景：200/500/1000 轮对话压测。
- 指标覆盖：代码任务成功率、历史指令保持率、TTFT、token 成本、缓存命中率。
- 建立回归门槛，作为发布前必过标准。

## 8.5 针对当前代码的必要修正项（状态更新）

- 已完成：消息检索角色范围修正（`user + assistant`）。
- 已完成：检索作用域修正（优先会话内接口）。
- 已完成：历史入口收敛（统一 `ListWindow`，保留降级回退）。
- 新增待办：记忆去重策略从“写入时去重”扩展为“离线重整任务”，周期清理历史重复项。
- 新增待办：首轮记忆加载引入观测指标（首轮命中率、首轮注入 token 占比）并接入告警。

## 9. 升级顺序建议

1) 先完成 P1 的数据库级分页查询（收益最大、风险最低）  
2) 再落地 Task State 与结构化压缩（提升质量稳定性）  
3) 最后推进 P2 的分层摘要索引与自动评测闭环

## 10. 风险与回滚

- 风险 1：分页策略误裁剪导致历史缺失  
  - 方案：保留可配置窗口和降级开关，异常时回退到 P0 路径。
- 风险 2：Task State 与自然语言历史不一致  
  - 方案：注入时以最新工具结果校准，并保留冲突日志。
- 风险 3：结构化压缩误提取  
  - 方案：保留原文片段兜底，失败时回退通用摘要策略。
- 风险 4：分页上线导致消息顺序异常  
  - 方案：上线前增加“同时间戳顺序一致性”回归测试，异常时自动回退全量读取。
- 风险 5：角色扩展后召回噪声增加  
  - 方案：引入角色权重与阈值控制，assistant 召回默认低于 user，逐步灰度。

## 11. 上线执行清单（防回归）

- 第一步：上线 DB 分页查询与服务层 `ListWindow`，开启日志观测，不切流量。
- 第二步：灰度切换 Agent 历史加载到 `ListWindow`，监控加载耗时与上下文大小。
- 第三步：开启检索角色扩展与作用域过滤，监控召回质量指标。
- 第四步：上线 Task State 注入与结构化压缩，执行代码任务回归集。
- 第五步：通过 200/500/1000 轮压测后，放开默认策略并保留回滚开关。

## 12. 下一阶段优化项目（更新）

1) 记忆去重升级  
- 增加离线去重作业：按 `category + embedding` 聚类，合并高相似重复项。  
- 引入去重阈值配置：支持按类别配置阈值（偏好类更严格、经验类更宽松）。  

2) 首轮记忆质量治理  
- 增加首轮记忆命中评测：任务型/编码型场景下首轮必须命中 L1+L2。  
- 增加首轮保护策略：当首轮未命中关键记忆时自动触发一次补检索。  

3) 观测与回归  
- 报表新增指标：重复记忆率、首轮记忆命中率、会话外召回占比。  
- 发布门槛新增硬指标：重复记忆率持续下降且首轮命中率达标后方可全量。

## 13. 离线去重执行方式

- 已提供命令：`auramate memory-dedup`。
- 默认模式为演练：`--dry-run=true`，只输出统计不删数据。
- 正式执行示例：`auramate memory-dedup --dry-run=false --threshold=0.92`。
- 推荐策略：
  - 首次上线先跑一次 `dry-run`，确认重复规模。
  - 再执行一次 `apply` 清理历史存量。
  - 后续按周或按数据量阈值周期执行。
