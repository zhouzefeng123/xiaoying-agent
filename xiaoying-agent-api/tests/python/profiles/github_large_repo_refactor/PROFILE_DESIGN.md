# GitHub 大仓 profile 设计约束

## 目标

第二条及后续真实仓库 profile，必须比 `django_http_allowed_hosts.json` 更接近大型项目重构，但仍然保持可重复评分。

## 最低门槛

- 固定 `repo_ref`，并能记录唯一 `source_commit`
- 至少修改 `4` 个文件
- 必须同时覆盖：
  - 一个核心实现文件
  - 至少两个调用方或协作模块
  - 一个测试文件
- 必须保留公开 API 与既有行为
- 必须配置至少一条行为验证命令，不能只做语法检查
- 必须声明：
  - `expected_paths`
  - `allowed_changed_paths` 与 `max_changed_files`，用于约束大仓重构的改动边界
  - `required_content_markers`
  - 视情况声明 `forbidden_content_markers`

## 推荐题型

优先选择这些任务：

1. 提取共享 helper，并更新多个调用方与回归测试
2. 收敛重复校验或重复转换流程，并保持外部接口不变
3. 把散落在多个模块中的同类逻辑集中到已有合理归属处

## 暂不接受的题型

- 只改一个函数名或一处局部文本
- 只靠 `py_compile` 就能判定正确的任务
- 需要大规模架构重写、迁移框架或改公共 API 的任务
- 必须依赖不稳定外部服务、数据库或网络才能验证的任务

## 候选筛选清单

挑题前先确认：

1. 现有代码里确实存在重复逻辑，而不是人为制造伪重复
2. 目标 ref 下有足够稳定的测试支点
3. 至少能写出一条明确的“应出现结构”和一条明确的“应消失结构”
4. 续接轮还能提出有意义的复查动作，而不是天然无事可做
5. 任务完成后 diff 容易审计，失败时也容易定位原因

## 评分原则

通过不只代表“改了代码”，还必须同时满足：

- 首次写入前完整阅读所有 `expected_paths`
- 产生命中目标文件的可审计 diff
- agent 自己执行验证命令
- 续接轮继续执行并重新验证
- 完整长链 profile 至少三轮，且每一轮都必须有真实工具执行和验证命令
- 必要结构出现、禁止结构消失
- 全部配置验证命令通过
